## 2. 🔍 [INFERENCE] 벤치마크 하드닝을 통해 밝혀진 사실

1. **지연시간 역수(Latency-Equivalent FPS) vs 실측 처리량(Throughput FPS)의 혼동 해소**:
   * 이전 단일 Trial에서 보고된 `23.3 FPS`는 **프레임 지연시간의 역수(`1000 / 42.86ms`)**였으며, 실제 10초 동안 화면에 렌더링된 **실제 초당 프레임 처리량(Throughput)**은 약 **2~3.1 FPS** 수준이었습니다.
2. **SurfaceFlinger 프로퍼티 튜닝 가설 검증**: **【 성능 향상 없음 / 오히려 역효과 확인 】**
   * `latch_unsignaled=1` 단독 적용 시 처리량 변화 없음 (3.09 ➔ 2.97 FPS).
   * `disable_backpressure=1` 적용 시 버퍼 큐 스톨과 프레임 드랍이 증가하여 처리량이 **3.09 ➔ 1.97~2.02 FPS로 오히려 하락**.
   * **결론**: 게스트 OS의 `SurfaceFlinger` 큐 튜닝은 1920×1200 고해상도 병목의 근본 해결책이 아니며, **기본값(Baseline)으로 두는 것이 가장 안정적**입니다.
3. **품질 게이트(Sample Validity Gate) 정상 작동**:
   * Condition D Trial 1에서 Instagram 피드가 일시 멈추어 6개 프레임만 기록되었을 때, 이를 자동으로 `INVALID / INSUFFICIENT_SAMPLES`로 분류하여 통계 왜곡을 방지했습니다.

## 3. 🛠️ [IMPLEMENTED] 구현 및 코드 변경 내역

1. **[`scripts/windows/benchmark-spike.ps1`](../../scripts/windows/benchmark-spike.ps1)**:
   * `ThroughputFps` (`ValidFrames / ActualDurationSec`)와 `FrameLatencyAvgMs` / `LatencyEqFps` (`1000 / Latency`) 명확히 분리.
   * 15프레임 미만 샘플 자동 `INVALID` 필터링 게이트 적용.
   * 워크로드 진행 중 350ms 주기로 QEMU CPU(평균/피크) 및 Windows GPU 3D/Copy 엔진 카운터 지속 샘플링.
   * `setprop` 후 `getprop` 자동 Read-back 검증 로직 추가.
   * 4-Way 매트릭스 x 5회 반복 측정 및 `Median`, `Min`, `Max`, `StdDev` 통계 자동 산출.
2. **[`TabletDroid.Core/Models/RuntimeConfiguration.cs`](../../host/TabletDroid.Core/Models/RuntimeConfiguration.cs)**:
   * `EnableSurfaceFlingerLowLatencyTuning`을 **기본값 `false`의 실험용 플래그**로 분리 (조용한 프로덕션 기본 주입 방지).
3. **[`TabletDroid.Runtime/AndroidEmulatorBackend.cs`](../../host/TabletDroid.Runtime/AndroidEmulatorBackend.cs)**:
   * 실험 플래그 활성화 시에만 프로퍼티를 주입하고, `getprop` Read-back 결과를 `DiagnosticLogService`에 정확히 기록.
4. **[`TabletDroid.Tests/BenchmarkMetricsTests.cs`](../../host/TabletDroid.Tests/BenchmarkMetricsTests.cs)**:
   * Throughput vs Latency 분리, 샘플 유효성 게이트, 백분위수(P50/P90/P99), 다중 Trial 통계 계산 단위 테스트 4건 추가.
   * 전체 19건 단위 테스트 100% 통과 (`19 Passed, 0 Failed`).
